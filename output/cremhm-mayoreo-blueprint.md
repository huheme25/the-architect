## 1. Project Overview

### Vision
**CremHM Mayoreo** es el portal de pedidos mayoristas de Cremería HM. Los clientes mayoristas inician sesión, ven el catálogo **con el precio de su lista asignada**, arman un pedido (carrito → checkout con fecha de entrega y notas), y lo envían. Internamente, el pedido se **explota por bodega** (secos, refrigerados, barra): cada almacenista ve su cola de surtido, marca los renglones que le corresponden y captura la cantidad real surtida; cuando todas las bodegas terminan, el pedido pasa a "listo para entrega". El equipo gestiona clientes, enriquecimiento de catálogo (bodega/presentación por producto) y da seguimiento desde dashboards por rol.

Reemplaza un prototipo de Base44 (`cremhm-beta`) que validó el dominio pero no es productivo. Esta versión es real: precios en vivo desde el POS, totales y folios calculados en el servidor, y el flujo de surtido completo que el prototipo dejó a medias.

### Goals
- Que los 25 clientes del lanzamiento pidan en línea viendo **su** precio (no precio público).
- Eliminar el ruteo manual de pedidos a bodega: tickets automáticos por almacén.
- Cero duplicación de precios: PuntoZero es la única fuente de verdad de catálogo y precios.
- Construir aislado de EspritOS, con convenciones idénticas para fusionar después sin fricción.

### Success Metrics
- 25 clientes activos pidiendo en línea en el primer mes.
- 100% de los pedidos ruteados a bodega automáticamente (sin captura manual).
- Tiempo de captura de pedido < 5 min por cliente.
- Cero incidentes de escritura accidental a PuntoZero.

### No-goals (v1) — se agregan al fusionar con EspritOS
- Inventario / control de stock.
- Facturación CFDI.
- Crédito / cuentas por cobrar.
- Pagos en línea.

## 4. Data Model

Tres orígenes de datos: **PuntoZero (RO)**, **enriquecimiento local (RW)**, **pedidos (RW)**.

### 4.1 PuntoZero — modelos `unmanaged` (COPIAR del portal, NO modificar)

**PzProducto** (`db_table="productos"`, `managed=False`, DB `puntozero`)
| Campo | Tipo | Notas |
|-------|------|-------|
| clave | CharField(20) PK | `db_column="Clave"` — id del producto |
| descrip | CharField(254) | `db_column="Descrip"` — nombre/descripción (incluye presentación en texto) |
| linea_id | IntegerField | `db_column="Linea"` — FK lógica a PzLinea |
| precio1..precio5 | DecimalField(12,2) | `db_column="Precio1".."Precio5"` — las 5 listas |
| descuento | DecimalField | `db_column="Descuento"`, nullable — % general |
| en_lista | SmallIntegerField | `db_column="EnLista"` — flag de visibilidad |

Método clave (copiar tal cual):
```python
def precio_para(self, nivel: int) -> float:
    nivel = nivel if 1 <= nivel <= 5 else 1
    precio_base = getattr(self, f"precio{nivel}") or self.precio1
    descuento = float(self.descuento or 0)
    return round(float(precio_base) * (1 - descuento / 100), 2)
```

**PzLinea** (`db_table="lineas"`): `id` (PK, `db_column="Id"`), `linea` (CharField, `db_column="Linea"`). Categoría del producto.

**PzCliente** (`db_table="clientes"`): `clave` (PK), `nombre`, `precio` (SmallInteger, `db_column="Precio"` → nivel 1-5), `telefono1..4`, `email`, `suspendido` (0=activo), `clasificacion`. Propiedades `celulares_normalizados` y `activo`.

### Relationships
- `Pedido` 1—N `LineaPedido`.
- `Pedido.cliente_clave_pz` → `PzCliente.clave` (lógica, cruza DBs).
- `LineaPedido.clave_pz` → `PzProducto.clave` (lógica) y `ProductoMayoreo.clave_pz` (para bodega).
- `User.clave_cliente_pz` → `PzCliente.clave` (lógica). Vendedor/admin/almacenista no tienen `clave_cliente_pz`.

### Regla de oro de precios (defensiva, heredada del portal)
El nivel del cliente se resuelve por request con `user.precio_efectivo` (prospect/anónimo **siempre** nivel 1, hardcodeado en la vista — nunca confiar solo en el campo). Al **crear** la línea de pedido se congela `precio_unitario = pz_producto.precio_para(user.precio_efectivo)`. Después de eso el precio del pedido no cambia aunque cambie PZ.

## 5. API Design

v1 es **server-rendered con HTMX** (HTML, no JSON). No hay API REST pública. Las "rutas" son vistas Django que devuelven página completa o parcial según `request.htmx`.

### Rutas (vistas) principales
| Método | Path | Descripción | Acceso |
|--------|------|-------------|--------|
| GET | `/` | Landing/redirect según rol | público→login |
| GET/POST | `/accounts/login/` | Login staff (usuario/contraseña) | público |
| GET/POST | `/accounts/otp/` | Login cliente (envía/valida OTP WhatsApp) | público |
| GET | `/catalogo/` | Catálogo con precio del cliente; filtros HTMX | cliente |
| POST | `/carrito/agregar/` | Agrega línea (HTMX, devuelve `_carrito.html`) | cliente/vendedor |
| POST | `/carrito/actualizar/` | Cambia cantidad/elimina (HTMX) | cliente/vendedor |
| GET/POST | `/pedidos/checkout/` | Confirma pedido (fecha entrega, notas) → crea Pedido | cliente/vendedor |
| GET | `/pedidos/` | Lista de pedidos (scoped por rol) | todos |
| GET | `/pedidos/<folio>/` | Detalle + acciones de estado | todos (scoped) |
| POST | `/pedidos/<folio>/estado/` | Avanza/cambia estado (HTMX) | vendedor/admin |
| GET | `/pedidos/<folio>/ticket/<bodega>/` | PDF ticket de surtido por bodega (WeasyPrint) | almacenista/admin |
| GET | `/surtido/` | Cola del almacenista (su bodega) | almacenista |
| POST | `/surtido/linea/<id>/` | Marca surtido + cantidad real (HTMX) | almacenista |
| GET | `/admin-catalogo/` | Enriquecimiento (bodega/presentación/visible) | admin |
| POST | `/admin-catalogo/importar/` | Carga masiva CSV de bodegas | admin |
| GET | `/admin-clientes/` | Gestión + invitación de clientes | admin/vendedor |
| GET | `/dashboard/` | Métricas por rol | todos |

### Endpoints clave — detalle

**POST `/pedidos/checkout/`** (servicio `crear_pedido`)
- Input: carrito en sesión/DB temporal + `fecha_entrega?`, `notas?`.
- Lógica (`@transaction.atomic`): resuelve `nivel = user.precio_efectivo`; por cada ítem congela `precio_unitario = PzProducto.precio_para(nivel)`, `bodega = resolver_bodega(clave_pz)`, `subtotal`; suma `total`; genera `folio` con `DocumentSequence.next("PED", sucursal.codigo)`; crea `Pedido` + `LineaPedido[]`; dispara email de confirmación (Celery). Vacía carrito.
- Validación: cliente con `clave_cliente_pz` activo; vendedor solo para clientes asignados; cada producto `visible_mayoreo=True`; cantidad > 0.
- Errores de dominio: `ClienteInactivo`, `ProductoNoDisponible`, `CarritoVacio`.

**POST `/surtido/linea/<id>/`** (servicio `marcar_surtido`)
- Input: `cantidad_surtida`.
- Lógica (`@transaction.atomic`): valida que el almacenista pertenece a `linea.bodega`; setea `estado_linea="surtido"`, `cantidad_surtida`, `surtido_por`, `surtido_at`; llama `recalcular_estado_pedido(pedido)` → si **todas** las líneas de **todas** las bodegas están `surtido`, el pedido pasa a `listo_para_entrega` y dispara email "listo para entrega".

### Patrón HTMX dual-render (heredado del portal)
Cada vista detecta `request.htmx`: si es petición HTMX devuelve **solo el parcial** (`partials/_tabla.html`); si no, la página completa con `base.html`/`base_cliente.html`. Filtros, paginación, carrito y cambios de estado intercambian HTML, no JSON. Alpine.js solo para interactividad local (drawer del carrito, toasts, modales de confirmación).

```
    │   └── catalogo/partials/_card_producto.html (imagen, nombre, presentación, precio, +/- cantidad)

```

### State Management
- Estado de servidor: queries Django con `select_related`/`prefetch_related` (sin N+1; test de performance falla si una vista hace > 20 queries).
- Carrito: tabla temporal en Postgres propio (`CarritoItem` por usuario) o sesión — usa tabla DB para persistir entre dispositivos. Se vacía al crear el pedido.
- Catálogo: `@cache_page(60*5)` + `@vary_on_headers("HX-Request")` para lecturas a PZ (igual que el portal). El precio del cliente se resuelve fuera del cache key compartido — cachea el catálogo público (nivel 1) y resuelve niveles autenticados sin cache compartido, o incluye el nivel en la clave de cache.

## 8. Authentication & Authorization

### Dos caminos de auth, un solo modelo `User`
**User custom** (`AUTH_USER_MODEL = "accounts.User"`): `celular` (USERNAME para clientes), `username`/`password` (para staff), `clave_cliente_pz` (UNIQUE, null para staff), `precio_asignado` (int 1-5), `is_prospect`, `rol`. Propiedad `precio_efectivo` (prospect → 1, si no → `precio_asignado or 1`).

- **Equipo interno** (admin, vendedor, almacenista): `django-allauth`, login usuario/contraseña, MFA TOTP opcional. Los crea el admin.
- **Clientes mayoristas**: **WhatsApp OTP** (Twilio Verify, backend `OtpBackend` del portal). **Alta por invitación**: el equipo crea/vincula el cliente (teléfono ↔ `PzCliente.clave` activo vía `match_pz_client`), el cliente entra con su celular + código OTP. Sin contraseñas.

### Flujo de alta de cliente (invitación)
1. Admin/vendedor en `/admin-clientes/` busca el `PzCliente` (por clave/nombre) y captura el celular.
2. `invite_cliente()` valida con `match_pz_client(clave, celular)` que el celular pertenece a un cliente PZ **activo**; crea `User(clave_cliente_pz=clave, precio_asignado=pz.precio, is_prospect=False, rol="cliente")`.
3. El cliente recibe aviso (WhatsApp/email) y entra en `/accounts/otp/` con su celular → OTP → catálogo con su lista.

### Rutas protegidas
`LoginRequiredMiddleware` allowlist-based (todo protegido salvo `PUBLIC_PATTERNS`: landing, login, OTP, health). Además `ModuloRequiredMiddleware` mapea prefijo de URL → módulo/rol (RBAC). **Toda app nueva registra su prefijo** en `URL_TO_MODULO` o queda abierta.

### Roles & Permisos
| Rol | Puede |
|-----|-------|
| `admin` | Todo: pedidos (cualquier estado), enriquecimiento de catálogo, clientes, usuarios, dashboards globales, tickets |
| `vendedor` | Crear pedidos **solo para sus clientes asignados**, ver/editar sus pedidos (estados tempranos), dashboard propio |
| `almacenista` | Ver cola de **su bodega**, marcar surtido + cantidad real, imprimir ticket de su bodega |
| `cliente` | Catálogo con su precio, crear pedido para su propio negocio, ver su historial |

### Row-Level Security (obligatorio, patrón EspritOS)
Cada ListView usa `RoleFilteredQuerysetMixin` con `role_field_map` (ej. `{"vendedor": "creado_por", "cliente": "cliente_clave_pz"}`); roles en `unrestricted_roles` (admin) ven todo. **Tests RLS obligatorios por vista.**

### Session Management
Sesiones en Redis, 12h con sliding expiration (paridad EspritOS). OTP de cliente verifica vía Twilio y crea sesión normal.

```markdown
## Architecture

### Directorios
- `config/` — proyecto Django (split settings, celery, db_routers). NO se llama "cremhm".
- `apps/core/` — modelos abstractos, DocumentSequence (folios), RBAC, RLS mixins, backend MySQL legacy, router. Base de todo.
- `apps/accounts/` — User custom; staff por contraseña (allauth), clientes por WhatsApp OTP.
- `apps/catalogo/` — modelos RO de PuntoZero (PzProducto/PzCliente) + ProductoMayoreo (enriquecimiento RW: bodega/presentación/visible).
- `apps/pedidos/` — Pedido/LineaPedido, carrito, checkout, estados.
- `apps/surtido/` — cola por bodega, captura de surtido, tickets PDF.
- `apps/dashboard/` — métricas por rol.

### Data Flow
Catálogo y precios se LEEN en vivo de PuntoZero (RO) vía modelos `unmanaged` + router que bloquea writes. La bodega de cada producto vive en `ProductoMayoreo` (local). Al crear pedido se CONGELA precio (`PzProducto.precio_para(user.precio_efectivo)`), bodega y subtotal en LineaPedido. Pedidos viven en Postgres propio. Surtido rutea líneas por bodega; cuando todas se surten, el pedido pasa a "listo_para_entrega".

### Key Patterns
- **Lógica en `services.py`, queries en `selectors.py`, vistas delgadas.** Vistas solo orquestan.
- **HTMX dual-render**: `if request.htmx` → parcial `partials/_*.html`; si no → página completa.
- **RLS por vista** con `RoleFilteredQuerysetMixin` + `role_field_map`. Test RLS obligatorio.
- **Folios atómicos** vía `DocumentSequence.next("PED", sucursal.codigo)`.
- **Precio defensivo**: prospect/anónimo SIEMPRE nivel 1, hardcodeado en la vista.

## Code Organization Rules

1. Apps solo importan de `core` y de sí mismas (cross-app vía services con import diferido).
2. Imports absolutos siempre (`from apps.catalogo.models import ...`).
3. Modelos heredan los abstractos de `core`; `db_table` explícito en español; `CheckConstraint` para invariantes (total ≥ 0, cantidad > 0).
4. Variables de entorno SOLO vía `env()` de django-environ. Nunca `os.environ.get`.
5. Templates: comentarios multilínea SOLO con `{% comment %}...{% endcomment %}`, nunca `{# #}` partido en varias líneas (rompe el render).
6. Migraciones aplicadas NUNCA se editan — crea una nueva.
7. Toda app nueva registra su prefijo de URL en `URL_TO_MODULO` del middleware o queda abierta.
```

## 16. Reglas No Negociables (para el builder)

1. **PuntoZero es solo lectura, sin excepción.** Router bloquea writes; modelos PZ `managed=False`; test `critical` que falla si algo intenta escribir. Persiste pedidos solo en el Postgres propio.
2. **Dinero y folios en el servidor.** Congela `precio_unitario`/`bodega`/`subtotal` al crear la línea; `total` server-side con `CheckConstraint ≥ 0`; folio vía `DocumentSequence` atómico. El cliente nunca calcula precios.
3. **Paridad con EspritOS.** Mismo stack, versiones, estructura (`config/`, `apps/`), abstractos de `core`, patrón services/selectors, split settings con django-environ. El objetivo es fusionar después sin reescribir.
4. **Reusa, no reinventes.** Copia del portal: modelos `unmanaged` de PZ, `precio_para`, router multi-DB, backend MySQL legacy (latin1), `auth_otp`, `money_mxn`, normalización de teléfono. No los escribas desde cero.
5. **Diseño claro de marca HM** (sección 7), NO el dark de EspritOS. Crema `#FEFCF9`, azul `#1D3A89`, Playfair + Inter. Mobile-first (los clientes piden desde el celular).
6. **RLS y RBAC obligatorios**, con tests por vista. Toda app registra su prefijo en `URL_TO_MODULO`.
7. **Alcance v1 cerrado:** features del prototipo Base44 + flujo de surtido completo. Sin inventario, CFDI ni crédito (post-merge a EspritOS).
8. **`resolver_bodega()` es el único punto de cambio para la V2** (cuando la bodega se lea desde PZ). No riegues la lógica de bodega por todo el código.
