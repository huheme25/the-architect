## 1. Project Overview

### Visión

**portal-cremeriahm** es el portal web de clientes mayoristas de Cremería HM, expuesto en `portal.cremeriahm.com`. Reemplaza el flujo manual de "el vendedor manda la lista de precios por WhatsApp" con un sitio donde cada cliente inicia sesión y ve **su lista de precios personalizada** (Precio 1 a 5, según asignación en PuntoZero).

Es un **proyecto Django independiente** que comparte el servidor físico de EspritOS (WSL2 Ubuntu en 192.168.0.152) pero está **aislado a tres niveles**:

1. **Proceso** — container Docker propio, runtime separado.
2. **Datos** — role Postgres `portal_user` con permisos mínimos sobre vistas readonly. Sin acceso al schema interno de EspritOS (POS, facturación, CRM).
3. **Red** — Cloudflare Tunnel propio, sub-dominio dedicado, WAF independiente.

Esto evita que una vulnerabilidad pública en el portal comprometa el core ERP/POS/CRM que vive en EspritOS.

La autenticación es **passwordless** vía OTP (One-Time Password) por email + WhatsApp. El cliente nunca define contraseña: cada login envía un código de 6 dígitos al canal elegido. El **celular** es la ancla de identidad, lo que prepara el portal para el roadmap de fidelización/recompensas (cada canje requerirá OTP fresco al titular del celular).

El registro es self-service. Si el cliente provee una **Clave de Cliente** que existe en PuntoZero **y un celular que coincide con alguno de los 4 teléfonos en `clientes`**, queda verificado con su precio asignado. Si la Clave no existe o el celular no coincide, queda registrado como **prospecto** (solo ve precio público — Precio1) y se le da seguimiento desde un dashboard interno.

### Goals

- **Sustituir el envío manual de listas de precios** por WhatsApp/email. Cada cliente entra al portal y ve su precio en tiempo real.
- **Captar prospectos**. Visitantes que no son clientes registrados se quedan capturados con celular y nombre — input gratis para el equipo comercial.
- **Aislar el portal del ERP**. Una vulnerabilidad en el portal no debe poder leer ni modificar nada de EspritOS.
- **Cero costo SaaS de auth**. Django auth + OTP propio. Sin Clerk, sin Auth0.
- **Costo total ≤ 20 USD/mes** para 300 clientes activos (incluye WhatsApp).
- **Lanzamiento MVP en ≤ 3 semanas** desde día 1 (con email-only). WhatsApp se agrega cuando Meta apruebe (~día 5).

### Success Metrics

- **Cobertura de registro:** ≥ 70% de clientes mayoristas activos registrados en los primeros 60 días.
- **Time-to-first-login** ≤ 90 segundos desde "abro el portal" hasta "veo mis precios".
- **Tasa de fallo de OTP** < 5% (medida: OTPs enviados sin login completado por canal).
- **Tasa de prospectos auto-capturados** ≥ 10% del tráfico no autenticado (señal de que el portal sirve también de canal comercial).
- **Cero incidentes de aislamiento** EspritOS ↔ portal en los primeros 6 meses.

## 2. Tech Stack

| Layer | Technology | Why |
|-------|-----------|-----|
| Framework | **Django 5.1** + Python 3.12 | Mismo stack que EspritOS, reuso de conocimiento de Beto. Ecosistema sólido para auth/sessions/admin. |
| Frontend | **HTMX 2 + Alpine 3 + Tailwind v4** | Server-rendered, sin SPA. Idéntico a EspritOS. Bundle JS mínimo, deploy simple. |
| Templates | **Django Templates** | Nativo. Sin pre-render JSX innecesario para 30 páginas. |
| Auth | **Custom passwordless OTP** sobre `django.contrib.auth` | Identidad anclada al celular. Sin contraseñas (sin recovery flows). $0 SaaS. |
| Database (transactional) | **Postgres 16** (mismo servidor que EspritOS, distinto role) | Reusa infra existente. Schema `portal` aislado del schema `espritos`. |
| Database (readonly source) | **MySQL 5.1 PuntoZero** (192.168.0.200/datos1) | Fuente de verdad de clientes y productos. Lectura via user `portal_reader` con permisos mínimos. |
| ORM | **Django ORM** | Estándar Django. Multi-DB router para Postgres + MySQL simultáneo. |
| Session storage | **Postgres-backed** (django-session) | Revocables del lado servidor. Mejor que cookies firmadas para portal con datos de cliente. |
| Email OTP | **Resend + django-anymail** | 3,000 emails/mes free tier. Deliverability de primer mundo. SDK trivial. |
| WhatsApp OTP | **Meta WhatsApp Cloud API** (directa, sin Twilio) | Free tier 1,000 conversaciones/mes. ~$0.0095/msg después en MX. Mucho más barato que Twilio. |
| OTP hashing | **Argon2** (`argon2-cffi`) | Mismo hash que Django para passwords. Resistente a brute-force aún con hashes filtrados. |
| Rate limiting | **django-ratelimit** | 5 intentos OTP/hora por celular, 10/hora por IP, 3 registros/hora por IP. |
| Forms | **Django Forms + crispy-tailwind** | Server-rendered, validación nativa. Crispy aplica clases Tailwind sin configuración manual. |
| Tablas | **HTML semántico + HTMX para sort/filter** | 2,400 productos visibles en una tabla con paginación HTMX. Sin TanStack Table. |
| Icons | **Heroicons** (CDN) o **Lucide static** | Pesados < 10kb, integrables en templates Django. |
| Deployment | **Docker Compose** + **Cloudflare Tunnel** | Servicio adicional en mismo `docker-compose.prod.yml` que EspritOS, pero tunnel separado. |
| Static assets | **WhiteNoise** | Sirve estáticos sin nginx separado. Gzip + cache headers. |
| Logging/audit | **Postgres `portal.audit_log`** + Cloudflare Access logs | Cada login, OTP solicitado, OTP usado, cambio de celular queda en DB. Forense si hay incidente. |
| Backups | **pg_dump diario** del schema `portal` (cron en host) | El servidor Postgres ya tiene backups generales, este es backup específico del schema portal. |
| CI | **GitHub Actions** | Lint (ruff), test (pytest-django), build de imagen Docker. |
| Package manager | **uv** (Python) | Ultrarrápido vs pip. Estándar moderno. Mismo que EspritOS. |

**Stack que NO usamos y por qué:**

| Tecnología | Por qué la rechazamos |
|------------|----------------------|
| Next.js / React | Innecesario. 95% del portal es server-rendered (login, tabla de precios, formulario). HTMX cubre el 5% interactivo. |
| Clerk / Auth0 / iron-session | Beto evita SaaS de auth. Custom passwordless es ~200 líneas Django. |
| Twilio Verify API | Caro ($0.05/verificación → ~$120/mes). Implementamos OTP propio, gratis. |
| Twilio WhatsApp | Más caro que Meta directa. Sin razón para intermediario. |
| SMS (cualquier provider) | $0.04-0.05/msg en MX. Mucho más caro que email/WhatsApp. WhatsApp es ubicuo en MX. |
| NextAuth | Es para Next.js. Y agrega dependencia que Django no necesita. |
| Vercel/Neon | Sería un stack distinto sin razón. EspritOS ya tiene infra. |
| Redis para OTP | Postgres es suficiente para 300 clientes. Redis ya existe en EspritOS pero no necesitamos compartirlo (acoplamiento extra). |

### Vistas readonly en Postgres (compartidas con `portal_user`)

Estas vistas curadas son la **única superficie de datos PuntoZero que el portal puede leer**. El `portal_user` no tiene `SELECT` directo sobre las tablas reales — solo sobre estas vistas.

**`portal.v_clientes_publica`** (origen: `clientes` de PuntoZero, vía MySQL→Postgres ETL o foreign data wrapper)
```sql
CREATE OR REPLACE VIEW portal.v_clientes_publica AS
SELECT
  TRIM(c.Clave) AS clave_cliente,
  TRIM(c.Nombre) AS nombre_razon_social,
  c.Precio AS precio_asignado,
  -- Celulares normalizados a +52XXXXXXXXXX (todos los Telefono1..4 se exponen)
  ARRAY_REMOVE(ARRAY[
    portal.normalize_phone(c.Telefono1),
    portal.normalize_phone(c.Telefono2),
    portal.normalize_phone(c.Telefono3),
    portal.normalize_phone(c.Telefono4)
  ], NULL) AS celulares_registrados,
  c.Email AS email_registrado,
  (c.Suspendido = 0) AS activo
FROM espritos.pz_clientes c
WHERE c.Suspendido = 0;
```

**`portal.v_productos_publica`**
```sql
CREATE OR REPLACE VIEW portal.v_productos_publica AS
SELECT
  TRIM(p.Clave) AS clave_producto,
  TRIM(p.Descrip) AS descripcion,
  p.Linea AS linea_id,
  l.Linea AS linea_nombre,
  p.Precio1, p.Precio2, p.Precio3, p.Precio4, p.Precio5,
  COALESCE(p.Descuento, 0) AS descuento_pct,
  (p.EnLista = 1) AS visible
FROM espritos.pz_productos p
LEFT JOIN espritos.pz_lineas l ON p.Linea = l.Id
WHERE p.EnLista = 1
  AND p.Precio1 > 0;
```

> **Nota crítica:** Estas vistas asumen que **EspritOS ya hizo ETL** desde MySQL PZ a Postgres `espritos.pz_clientes` / `espritos.pz_productos`. Si la migración de Cremería (datos1) aún no termina, ver Sección 9 — Build Order Step 5 para el camino alternativo (lectura directa desde MySQL via Django multi-DB).

**`portal.normalize_phone(text)`** (función auxiliar)
```sql
CREATE OR REPLACE FUNCTION portal.normalize_phone(raw_phone TEXT)
RETURNS VARCHAR AS $$
DECLARE
  digits TEXT;
BEGIN
  IF raw_phone IS NULL OR LENGTH(TRIM(raw_phone)) = 0 THEN RETURN NULL; END IF;
  digits := REGEXP_REPLACE(raw_phone, '[^0-9]', '', 'g');
  IF LENGTH(digits) = 10 THEN RETURN '+52' || digits;
  ELSIF LENGTH(digits) = 12 AND LEFT(digits, 2) = '52' THEN RETURN '+' || digits;
  ELSIF LENGTH(digits) = 13 AND LEFT(digits, 3) = '521' THEN RETURN '+52' || RIGHT(digits, 10);
  ELSE RETURN NULL;
  END IF;
END; $$ LANGUAGE plpgsql IMMUTABLE;
```

### Permisos Postgres exactos

```sql
-- Role del portal (sin login a tablas reales, solo vistas)
CREATE ROLE portal_user WITH LOGIN PASSWORD '<gestionado en .env>';

-- Schema propio del portal (RW)
CREATE SCHEMA portal AUTHORIZATION portal_user;

-- Lectura SOLO sobre las vistas curadas
GRANT USAGE ON SCHEMA espritos TO portal_user;  -- necesario para resolver las vistas
GRANT SELECT ON portal.v_clientes_publica TO portal_user;
GRANT SELECT ON portal.v_productos_publica TO portal_user;

-- Negaciones explícitas (defensa en profundidad)
REVOKE ALL ON SCHEMA public FROM portal_user;
```

### Multi-DB router de Django

```python
# portal_cremeriahm/db_routers.py

class PortalDbRouter:
    """
    Lee/escribe sobre 'default' (Postgres como portal_user).
    Routea modelos unmanaged que mapean a MySQL PZ a 'puntozero' (modo readonly).
    En MVP step 5: si EspritOS ETL aún no termina, se usa esto.
    En producción definitiva: solo 'default' Postgres con vistas readonly.
    """
    PZ_MODELS = {'pzcliente', 'pzproducto', 'pzlinea'}

    def db_for_read(self, model, **hints):
        if model._meta.model_name in self.PZ_MODELS:
            return 'puntozero'
        return 'default'

    def db_for_write(self, model, **hints):
        if model._meta.model_name in self.PZ_MODELS:
            return None  # bloquea writes
        return 'default'

    def allow_relation(self, obj1, obj2, **hints):
        return obj1._state.db == obj2._state.db

    def allow_migrate(self, db, app_label, model_name=None, **hints):
        if model_name in self.PZ_MODELS:
            return False  # nunca migrar tablas PZ
        if db == 'puntozero':
            return False
        return db == 'default'
```

### Endpoints críticos en detalle

**POST `/registro/`**

Request body (form-encoded):
```
clave_cliente: "C00123"           (string, opcional — si ausente, se crea como prospect)
celular: "+523312345678"          (string, requerido, formato +52XXXXXXXXXX)
email: "cliente@ejemplo.com"      (string, opcional)
nombre_completo: "Don Joaquín"    (string, requerido)
canal_otp_preferido: "whatsapp"   (enum: 'email' | 'whatsapp', requerido)
```

Validaciones:
1. Celular formato MX válido (regex `^\+52\d{10}$` — auto-normaliza si vino como `33-1234-5678`).
2. Celular NO existe ya en `portal.user` (UNIQUE constraint).
3. Si `clave_cliente` provisto → query `portal.v_clientes_publica`:
   - **Match perfecto** (clave existe Y celular ∈ celulares_registrados): crea user con `is_prospect=False`, `precio_asignado=v.precio_asignado`, `clave_cliente_pz=clave`. Loggea `signup_attempt.match_result='match_full'`.
   - **Clave existe, celular NO coincide:** rechaza con error legible. Loggea `match_result='celular_no_coincide'`.
   - **Clave existe, cliente suspendido:** rechaza. Loggea `match_result='cliente_suspendido'`.
   - **Clave no existe:** crea user con `is_prospect=True`, `precio_asignado=1`. Loggea `match_result='clave_no_existe'`.
4. Si `clave_cliente` NO provisto: crea user como prospect.
5. Genera OTP, dispara al canal preferido.

Response: redirect 302 → `/verificar/`.

**POST `/verificar/`**

Request body:
```
codigo: "123456"                  (string, 6 dígitos)
```

Validaciones:
1. Sesión pre-auth contiene `pending_user_id` y `pending_otp_purpose`.
2. Busca último `OtpToken` de ese user no consumido y no expirado.
3. Verifica `argon2_verify(codigo, token.code_hash)`.
4. Si match: marca `consumed_at=NOW()`, autentica al user (Django `login()`), borra `pending_*` de sesión.
5. Si fail: incrementa `attempts`. Si `attempts ≥ 5`: invalida token, fuerza nuevo OTP.

Response:
- Éxito: redirect a `/mis-precios/` (autenticado) o `/precios/` (prospect).
- Falla: re-render con error.

**Rate limits aplicados (django-ratelimit):**

| Path | Key | Límite |
|------|-----|--------|
| POST `/registro/` | IP | 3/hora |
| POST `/login/` | IP | 10/hora |
| POST `/login/` | celular | 5/hora |
| POST `/verificar/` | session.pending_user_id | 10 intentos/10min |
| POST `/htmx/otp/reenviar/` | session | 1/min, 5/hora |

- **Server state es la verdad.** Todo se calcula en views Django y se renderiza HTML.

- Tabla de precios cacheada server-side por 5 min (`@cache_page(300)`) para anónimos. Para autenticados: cacheada por user durante 60 seg.
- ETag para HTML completo + `If-None-Match` (Django middleware nativo).
- Estáticos comprimidos por WhiteNoise con cache headers `max-age=31536000, immutable` (hash en filename).

## 8. Authentication & Authorization

### Auth Flow

**Registro**
```
1. GET  /registro/                     ← form
2. POST /registro/
        - Backend valida contra PZ:
          • Si match (clave + celular) → user.is_prospect=False, precio_asignado=PZ
          • Si solo celular sin clave → user.is_prospect=True, precio_asignado=1
          • Si clave existe pero celular falla → reject
        - Crea OtpToken (purpose='signup'), envía al canal preferido
        - Sesión guarda pending_user_id, pending_otp_purpose, pending_otp_destination
3. → 302 /verificar/
4. GET  /verificar/                    ← form 6 dígitos
5. POST /verificar/
        - Verifica argon2(codigo)
        - Marca otp.consumed_at, user.verified_at, login()
6. → 302 /mis-precios/  (o /precios/ si prospect)
```

**Login**
```
1. GET  /login/                        ← form (celular o email + canal)
2. POST /login/
        - Resuelve user por celular O email (UNIQUE)
        - Si no existe → "No encontramos tu cuenta. ¿Quieres registrarte?"
        - Crea OtpToken (purpose='login'), envía
3. → 302 /verificar/
4. POST /verificar/  → autentica → 302 /mis-precios/
```

**Cambio de celular** (autenticado)
```
1. GET  /mi-cuenta/cambiar-celular/    ← form
2. POST /mi-cuenta/cambiar-celular/    ← celular_nuevo
        - Crea PhoneChangeRequest (status=pending)
        - Genera 2 OTPs: uno al celular ANTERIOR, uno al NUEVO
3. Vista pide ambos códigos
4. POST → si ambos coinciden → user.celular = celular_nuevo, request.status=completed
        - Audit log
        - Notificación al celular_anterior: "Tu celular ha cambiado..."
```

### Protected Routes

| Path prefix | Auth requerida |
|-------------|----------------|
| `/`, `/precios/`, `/registro/`, `/login/`, `/verificar/`, `/static/` | No |
| `/mis-precios/`, `/mi-cuenta/`, `/logout/` | Sí (login_required) |
| `/admin/` | Staff |

Middleware: `LoginRequiredMiddleware` aplicado por allowlist (lista de rutas públicas, todo lo demás autenticado).

### Roles & Permissions

| Role | Definido por | Permisos |
|------|--------------|----------|
| Anónimo | Sesión sin user | Ver landing, precios públicos (Precio1), registrarse, login |
| Prospect | `user.is_prospect = True` | Ver precios públicos, ver "Tu cuenta es prospecto, contacta a tu vendedor para activar" |
| Cliente activo | `user.is_prospect = False` y vinculado a clave PZ | Ver sus precios (Precio_N) |
| Staff | `user.is_staff = True` | Acceso a Django admin: ver prospects, audit log, forzar reset de celular |

### Session Management

- Postgres-backed (`django.contrib.sessions.backends.db`).
- Cookie: `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=2592000` (30 días).
- Sliding expiration (`SESSION_SAVE_EVERY_REQUEST=True`).
- Logout invalida la sesión server-side (no solo borra cookie).
- Audit log en cada login_success/login_failed/logout.

### Password storage

- **No hay contraseñas.** El user model tiene `password='!'` (unusable) por convención de Django.
- **OTP se guarda como hash Argon2** en `code_hash`. El código plain solo existe en RAM y en el mensaje enviado.

```python
import uuid
from django.contrib.auth.models import AbstractBaseUser, BaseUserManager, PermissionsMixin
from django.db import models
from django.utils import timezone

class UserManager(BaseUserManager):
    def create_user(self, celular, nombre_completo='', email=None, **extra):
        if not celular: raise ValueError('celular requerido')
        user = self.model(celular=celular, email=email, nombre_completo=nombre_completo, **extra)
        user.set_unusable_password()
        user.save(using=self._db)
        return user

    def create_superuser(self, celular, password=None, **extra):
        extra.setdefault('is_staff', True)
        extra.setdefault('is_superuser', True)
        extra.setdefault('is_prospect', False)
        user = self.create_user(celular, **extra)
        if password: user.set_password(password)
        user.save(using=self._db)
```

```python
import re
def normalize_phone(raw: str | None) -> str | None:
    if not raw: return None
    digits = re.sub(r'\D', '', raw)
    if len(digits) == 10: return f'+52{digits}'
    if len(digits) == 12 and digits.startswith('52'): return f'+{digits}'
    if len(digits) == 13 and digits.startswith('521'): return f'+52{digits[3:]}'
    return None
```

```python
import secrets
from argon2 import PasswordHasher
from django.utils import timezone
from datetime import timedelta
from .models import OtpToken, User

from apps.audit.services import log_event

ph = PasswordHasher()

def generate_otp(user: User, purpose: str, channel: str, destination: str, ip: str, ua: str) -> OtpToken:
    code = f'{secrets.randbelow(10**6):06d}'
    token = OtpToken.objects.create(
        user=user,
        code_hash=ph.hash(code),
        channel=channel,
        destination=destination,
        purpose=purpose,
        expires_at=timezone.now() + timedelta(seconds=settings.OTP_TTL_SECONDS),
        ip=ip,
        user_agent=ua,
    )
    sender = get_sender(channel)
    sender.send_otp(destination=destination, code=code, purpose=purpose)
    log_event('otp_sent', user=user, ip=ip, payload={'channel': channel, 'purpose': purpose})
    return token

def verify_otp_code(user: User, purpose: str, code: str) -> bool:
    token = OtpToken.objects.filter(
        user=user, purpose=purpose, consumed_at__isnull=True, expires_at__gt=timezone.now()
    ).order_by('-created_at').first()
    if not token: return False
    if token.attempts >= settings.OTP_MAX_ATTEMPTS:
        return False
    try:
        ph.verify(token.code_hash, code)
    except Exception:
        token.attempts += 1
        token.save(update_fields=['attempts'])
        return False
    token.consumed_at = timezone.now()
    token.save(update_fields=['consumed_at'])
    return True
```

```python
from apps.precios.readonly_models.pz_clientes import PzCliente

def match_pz_client(clave: str | None, celular: str) -> dict:
    """Devuelve {'matched': bool, 'precio': int, 'cliente': PzCliente | None, 'reason': str}"""
    if not clave:
        return {'matched': False, 'precio': 1, 'cliente': None, 'reason': 'no_clave_provista'}
    try:
        cliente = PzCliente.objects.using('puntozero').get(clave=clave.strip())
    except PzCliente.DoesNotExist:
        return {'matched': False, 'precio': 1, 'cliente': None, 'reason': 'clave_no_existe'}
    if cliente.suspendido != 0:
        return {'matched': False, 'precio': 1, 'cliente': None, 'reason': 'cliente_suspendido'}
    celulares_pz = cliente.celulares_normalizados
    if celular not in celulares_pz:
        return {'matched': False, 'precio': 1, 'cliente': cliente, 'reason': 'celular_no_coincide'}
    return {'matched': True, 'precio': cliente.precio or 1, 'cliente': cliente, 'reason': 'match_full'}
```

```yaml
services:
```

- 1 container menos que mantener
- 1 token menos que rotar
- Misma observabilidad (logs en `cloudflared` único)

### Step 15: Cloudflare Tunnel + DNS — estrategia híbrida en 2 fases

**Decisión arquitectónica (revisión 2026-05-09):** se reutiliza el tunnel existente de EspritOS. No se crea uno nuevo.

#### Fase A — Beta cerrado en `portal.espritos.app` (semana 2-3)

`espritos.app` ya está en Cloudflare DNS (gestionado por el tunnel de EspritOS). Agregar el subdominio para el portal toma 5 minutos:

1. Cloudflare dashboard → Zero Trust → Networks → Tunnels → click el tunnel de EspritOS (el que sirve `espritos.app`).
2. Tab **Public Hostname** → **Add a public hostname**.
3. Configuración:
   - Subdomain: `portal`
   - Domain: `espritos.app`
   - Type: HTTP
   - URL: `portal:8000` (resuelve al container `portal` por nombre, dentro de la red `espritos_default`)
4. Save. `portal.espritos.app` resuelve y enruta al container.
5. En `.env.production` del portal:
   ```
   PORTAL_BASE_URL=https://portal.espritos.app
   DJANGO_ALLOWED_HOSTS=portal.espritos.app
   CSRF_TRUSTED_ORIGINS=https://portal.espritos.app
   ```

Beta con 5-10 clientes corre aquí. Validamos flujos. Cero impacto en `cremeriahm.com`.

#### Fase B — Lanzamiento masivo en `portal.cremeriahm.com` (semana 4-5)

Antes del lanzamiento masivo, migrar DNS de `cremeriahm.com` a Cloudflare. Hostinger sigue sirviendo el sitio estático; Cloudflare solo gestiona DNS + agrega el subdominio del portal.

**Pasos para Beto (manual, ~30 min + propagación 1-24h):**

1. **Cloudflare → Add a Site → `cremeriahm.com`** (plan Free).
2. Cloudflare auto-importa DNS records actuales de Hostinger:
   - A record raíz → IP del shared hosting de Hostinger (no se toca).
   - CNAME `www` → cremeriahm.com.
   - MX records si hay correo `@cremeriahm.com`.
   - TXT (SPF, DKIM, DMARC).
   **Revisar la lista detectada antes de continuar.**
3. Cloudflare entrega 2 nameservers (ej: `eva.ns.cloudflare.com`, `kai.ns.cloudflare.com`).
4. **Hostinger panel → Dominios → cremeriahm.com → Servidores DNS → Cambiar a personalizados** → pegar los 2 de Cloudflare → Guardar.
5. Esperar propagación. Verificar con:
   ```bash
   nslookup -type=ns cremeriahm.com 8.8.8.8
   ```
   Cuando muestre los nameservers de Cloudflare, listo.
6. En Cloudflare la zona pasa a "Active".
7. Verificar:
   - `cremeriahm.com` carga (Hostinger sigue sirviendo).
   - Mandar/recibir correo `@cremeriahm.com` si aplica.
   - El script `publicar_precios.py` sigue publicando vía git push (no afectado).
8. Agregar Public Hostname al tunnel (igual que Fase A):
   - Subdomain: `portal`
   - Domain: `cremeriahm.com`
   - Type: HTTP
   - URL: `portal:8000`
9. Actualizar `.env.production`:
   ```
   PORTAL_BASE_URL=https://portal.cremeriahm.com
   DJANGO_ALLOWED_HOSTS=portal.cremeriahm.com,portal.espritos.app
   CSRF_TRUSTED_ORIGINS=https://portal.cremeriahm.com,https://portal.espritos.app
   ```
   Mantener `portal.espritos.app` activo 2 semanas en paralelo (por si clientes beta lo bookmarkearon).
10. Botón en `cremeriahm.com` (Hostinger): editar HTML estático para agregar CTA "Acceso clientes" → `https://portal.cremeriahm.com/`. Subir vía git push (mismo flujo de `publicar_precios.py`).

**Lo que NO se rompe en la migración DNS:**
- Sitio estático en Hostinger sigue funcionando (Cloudflare gestiona DNS, Hostinger sigue siendo el origin).
- Correo `@cremeriahm.com` sigue funcionando si los MX migraron OK.
- Script `publicar_precios.py` no afectado.

**Lo que se desbloquea:**
- WAF + DDoS protection en `portal.cremeriahm.com`.
- Analytics de Cloudflare gratis.
- HTTPS automático sin lifting Hostinger.

**Por qué NO usar CNAME desde Hostinger DNS hacia el tunnel** (alternativa descartada):
Cloudflare Tunnel solo permite Public Hostnames cuyo dominio raíz esté gestionado por Cloudflare DNS. Un CNAME desde Hostinger DNS hacia `<tunnel-id>.cfargotunnel.com` falla con "domain not in your account". Por eso la migración DNS es necesaria, no opcional, para usar `cremeriahm.com`.

## 16. Reglas No Negociables

1. **Aislamiento Postgres es sagrado.** El role `portal_user` NUNCA debe tener `SELECT` directo sobre `espritos.*`. Solo sobre vistas. Cualquier nueva data de PZ que el portal necesite → nueva vista, nueva GRANT explícita. Defensa en profundidad.
2. **Sin contraseñas.** El sistema es passwordless. No agregar campo `password` al user model. Si en el futuro alguien lo pide "para emergencia", la respuesta es OTP fresco al admin.
3. **OTP en plain solo en RAM.** Generación → envío → hash a DB. Jamás `logger.info(code)`, jamás guardar en logs/audit el código plain.
4. **Rate limiting en TODOS los endpoints públicos.** signup 3/h por IP, login 10/h por IP + 5/h por celular, verify 10 intentos/10min por sesión, resend 1/min.
5. **Multi-DB con router estricto.** Modelos PZ siempre `managed=False`. Router bloquea `db_for_write` para esos modelos. Nunca un `migrate` sobre la DB `puntozero`.
6. **Celulares siempre normalizados.** Formato canónico `+52XXXXXXXXXX`. Validar al entrar (form), almacenar normalizado, comparar normalizado contra normalizado. La función `normalize_phone()` es la única vía.
7. **Vistas públicas devuelven Precio1 SIEMPRE.** No por query param. La función `get_precios()` recibe `precio_asignado` y lo respeta — pero en views públicas se hardcodea `=1`.
8. **Audit log es no-opcional.** Cada signup, login, otp_sent, otp_verified, phone_change, password_reset (no aplica), price_view, logout debe quedar registrado.
9. **WhatsApp solo después de aprobación Meta.** No usar números no-aprobados (que rompen TOS) ni servicios grises (Wassenger sin verificación). El portal arranca con email-only si Meta tarda.
10. **Sprint 0 (limpieza de celulares) es bloqueante de lanzamiento masivo.** Si la cobertura de celulares válidos < 85% en mayoristas activos, no se hace anuncio masivo — solo beta cerrado. La métrica define la fecha de lanzamiento.
11. **Cloudflare Tunnel sin puerto al host.** El container `portal` NUNCA expone puerto al host de WSL2. Acceso público es solo vía `cloudflared-portal`. Defensa en profundidad para que el ataque desde 192.168.x.x no toque el portal.
12. **Mover DNS de cremeriahm.com a Cloudflare antes del lanzamiento.** Sin esto pierdes WAF + DDoS + analytics. Hostinger sigue sirviendo `cremeriahm.com` raíz; Cloudflare solo gestiona DNS.
13. **Sin Twilio/intermediarios para WhatsApp.** Meta Cloud API directa. Más barato, menos cadena de custodia, menos lock-in.
14. **El script `publicar_precios.py` (AnalisisVentas) NO se toca.** Sigue publicando a `cremeriahm.com/precios.html` como hoy. El portal es un sistema independiente con su propia lectura de PZ.
15. **Si EspritOS cae, el portal cae también.** Es aceptable porque comparten servidor. El SLA del portal está atado al SLA de EspritOS — no se promete mejor. Si alguna vez se requiere SLA superior, mover el portal a un VPS dedicado (~$5-10 USD/mes) es trivial: solo cambiar `DATABASE_URL` para apuntar a la IP de EspritOS, abrir el firewall en Postgres, y mover el container.
