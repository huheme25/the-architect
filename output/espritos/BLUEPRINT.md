> **Nombre:** *EspritOS* — del francés *esprit* (espíritu, mente, inteligencia) + *OS* (operating system). El nombre captura la ambición del sistema: ser el espíritu operativo de Cremería HM — no solo un ERP, sino el cerebro que responde, razona y opera con el equipo.

## 0. Cómo usar este blueprint

Este documento es **autosuficiente**. Una instancia nueva de Claude Code, sin contexto previo, debe poder construir el proyecto siguiendo este blueprint paso a paso.

**Reglas de oro al construir:**
1. **No saltes pasos del Build Order.** Cada paso depende del anterior.
2. **No introduzcas dependencias que no estén en este blueprint** sin justificarlo en commit.
3. **Cada paso del Build Order debe terminar con un commit verificable** (tests pasando + manual smoke test).
4. **El usuario es Beto, su primera vez con Django.** Comenta el código en español cuando no sea obvio. No sobre-documentes.
5. **Si algo en el blueprint contradice una mejor práctica que conoces, pregunta antes de cambiarlo.**

## 1. Project Overview

### Vision

EspritOS es el sistema operativo interno de Cremería HM — una distribuidora de lácteos, embutidos y carnes en Tonalá, Jalisco con dos sucursales (Cremería y Abarrotera). El nombre viene del francés *esprit* (espíritu, mente, inteligencia) + *OS* (operating system): la meta es construir no solo un ERP, sino el **cerebro operativo** del negocio — un sistema que razona, responde preguntas en lenguaje natural, y opera con el equipo en lugar de imponerse sobre ellos.

EspritOS reemplaza dos sistemas que ya tocaron techo: el CRM-ERP v4 (Next.js + Prisma, monolito acoplado, deploy por USB, cada cambio rompe otra cosa) y Punto Zero (sistema legacy de punto de venta y ERP operacional).

El diferenciador principal es un **reporteador conversacional con IA**: cualquier supervisor de ventas puede preguntar en lenguaje natural — *"cuánta Salchicha San Antonio le vendí a FDH en marzo"* — y el sistema entiende, consulta la base de datos respetando sus permisos, devuelve la respuesta con tabla y gráfica, y opcionalmente genera un PDF formal con la marca Cremería HM.

A largo plazo absorbe las funciones de VentasHM (motor de comisiones), Expenses (control de egresos), los dashboards de AnalisisVentas, y **reemplaza por completo las 26 fases del CRM-ERP v4** (ver Apéndice D para el inventario completo de 72 modelos y el mapeo de fases). A corto plazo entrega valor desde la semana 5 con el reporteador IA leyendo datos históricos cargados desde `E:\Datos-PuntoZero\`.

### Alcance real (no subestimar)

Este proyecto **reemplaza un ERP operacional completo** — no es un "tool interno chico". El CRM-ERP v4 tiene:

- **72 modelos Prisma** en un schema de 1,543 líneas
- **26 fases GSD** documentadas con RESEARCH + PLAN + SUMMARY + VERIFICATION por cada una
- **Módulos críticos**: POS con hardware (impresora ESC/POS, báscula serial, lector barcode, cajón), motor de precios con cascada 4-niveles, CFDI 4.0 completo con Facturama (factura individual, global, standalone, NC, complementos de pago, cancelaciones), inventario con ledger append-only, comisiones con tiers progresivos, promociones NxM, bundles, programa de lealtad, CRM mayorista, PWA offline para rutero
- **Integración fiscal real**: certificados CSD, timbrado SAT, cancelación con motivos 01-04

EspritOS no es "un reporteador con IA + CRUD simples". Es el **reemplazo arquitectónico** de un ERP maduro. La ganancia no es "menos funcionalidad" — es "misma funcionalidad con cero regresiones entre módulos, tests obligatorios, y deploy automatizado".

### Goals

- **G1 — Quick-win IA (semanas 1-6)**: Entregar un reporteador IA funcional que responda preguntas reales del equipo de ventas con datos cargados de Punto Zero. Esto valida el stack y entrega valor inmediato mientras se construye el ERP.
- **G2 — Aislamiento modular**: Construir el ERP en 21 apps Django tan aisladas que un cambio en una **nunca** rompa otra — eliminar el dolor raíz del CRM-ERP v4. Enforced con test automático `tests/test_app_isolation.py`.
- **G3 — Deploy automatizado**: 100% desde GitHub vía Coolify — eliminar el deploy por USB. Primero en WSL2 de la PC del trabajo, luego en PC servidor dedicada en oficina.
- **G4 — Presupuesto estricto**: Operar dentro de $100-150 USD/mes total (API + cualquier servicio externo). Hosting on-prem en PC servidor de oficina = $0/mes de infraestructura.
- **G5 — Multi-rol + RLS real**: Soportar 25 usuarios internos con 5 roles (vendedor / supervisor_ventas / cobranza / almacenista / admin) y row-level security enforced en Python + tests E2E que verifican que vendedor no ve datos de otro vendedor.
- **G6 — Reemplazo gradual módulo por módulo**: Construir las 7 olas (A-G) del Build Order en secuencia lógica: catálogo → POS → facturación → compras/comisiones/gastos → CRM/promos/lealtad → dashboard/móvil → cierre. Nada de big-bang.
- **G7 — Paridad funcional con CRM-ERP v4**: Al terminar la Ola G, EspritOS debe soportar **100% de los casos de uso** del CRM-ERP v4, verificado con un checklist derivado de los 26 SUMMARY.md. No se apaga el sistema viejo hasta lograr paridad.
- **G8 — Tests obligatorios**: Cobertura mínima 80% por app, 100% en `sql_validator.py` y servicios atómicos del POS. Cero regresiones a producción.

### Success Metrics

- **M1 — Adopción IA**: 5 supervisores usan el chat IA al menos 10 veces por día durante la semana 6.
- **M2 — Cero USB**: Cero deploys manuales por USB después de la semana 4.
- **M3 — Estabilidad**: Menos de 1 bug regresivo por mes en módulos ya estables (vs CRM-ERP v4 donde "cada cambio rompe algo").
- **M4 — Presupuesto**: Costo mensual real ≤ $110 USD durante los primeros 3 meses.
- **M5 — Latencia IA**: Tiempo de respuesta del chat IA p95 < 8 segundos para queries simples, < 20s para complejas.
- **M6 — Paridad funcional**: 100% de los 26 SUMMARY.md del CRM-ERP v4 tienen su equivalente verificable en EspritOS antes de apagar el sistema viejo.
- **M7 — Velocidad POS**: Una venta completa en POS (desde escanear primer producto hasta imprimir ticket) en < 15 segundos con hardware real.
- **M8 — Cobertura de tests**: ≥ 80% línea por cada app, 100% en código crítico, verificado en CI.

## 2. Tech Stack

| Capa | Tecnología | Por qué |
|---|---|---|
| **Lenguaje** | Python 3.12 | Maduro, ecosistema rico para IA, ETL y web. Fácil para Beto de leer. |
| **Framework backend** | Django 5.1 | Admin gratis, ORM maduro, auth y permisos integrados. **Django *fuerza* modularidad** vía apps — soluciona "cada cambio rompe otra cosa" de raíz. Incluye DRF para API REST. |
| **API REST** | Django REST Framework 3.15 | Para futuro frontend móvil. Solo endpoints estrictamente necesarios al inicio. |
| **Frontend** | HTMX 2 + Alpine.js 3 + Django Templates | 25 users internos no necesitan React. ~10x menos código que mantener. HTMX da reactividad sin SPA. Alpine para interacciones locales (toggles, dropdowns). |
| **Estilos** | Tailwind CSS v4 + DaisyUI 4 | Tailwind v4 elimina configuración pesada. DaisyUI da componentes pre-hechos compatibles con HTMX (modales, drawers, tablas). |
| **Iconos** | Lucide (vía CDN o `lucide-static`) | Set consistente, gratuito, MIT. |
| **Charts** | ECharts 5 | Más potente que Chart.js para tablas densas y dashboards. Funciona con HTMX sin React. |
| **BD principal** | PostgreSQL 16 + extensión `pgvector` 0.7 | pgvector almacena embeddings de mensajes del chat para memoria semántica — sin meter otra base. |
| **Cache + colas** | Redis 7 | Cache de queries IA comunes (ahorra dinero), backend de Celery, sesiones Django. |
| **Workers** | Celery 5.4 + celery-beat | ETL nocturno desde Datos-PuntoZero, generación de PDFs en background, expiración de cachés. |
| **IA — generación SQL** | Anthropic API → **Claude Sonnet 4.6** (`claude-sonnet-4-6`) | Mejor calidad text-to-SQL en español para dominios de negocio. Razonamiento sobre schemas complejos. |
| **IA — clasificación** | Anthropic API → **Claude Haiku 4.5** (`claude-haiku-4-5-20251001`) | 3-5x más barato que Sonnet. Clasifica intención (simple / compleja / ambigua) antes de invocar Sonnet. |
| **SDK IA** | `anthropic` (Python) | SDK oficial. |
| **Validación SQL** | `sqlparse` 0.5 + parser custom | Bloquea cualquier statement que no sea SELECT, valida tablas/columnas contra whitelist, fuerza filtros de row-level security. |
| **PDFs** | WeasyPrint 62 | HTML+CSS → PDF. Plantillas versionables como código. Soporta logos, headers, footers, paginación. |
| **Auth** | django-allauth 65 + django-otp 1.5 (2FA opcional) | Gratis, multiusuario, soporta TOTP. Suficiente para 25 users internos. |
| **Permisos** | Django Groups + custom `RoleMixin` para querysets | Row-level filtering en Python (más fácil de mantener que RLS de Postgres y más fácil de testear). |
| **Forms** | django-crispy-forms + crispy-tailwind | Forms con styling automático Tailwind. |
| **HTTP frontend** | django-htmx 1.19 | Helpers para HTMX en Django (request.htmx, hx_trigger, etc.). |
| **ETL** | Polars 1.x + SQLAlchemy 2 (solo para ETL) | Polars es 10x más rápido que pandas para CSVs grandes. Beto ya lo usa en AnalisisVentas. |
| **Lectura XLS legacy** | `xlrd` 2.0 (.xls) + `openpyxl` 3.1 (.xlsx) | Datos-PuntoZero tiene ambos formatos. |
| **Containers** | Docker 27 + Docker Compose v2 | Mismo entorno en PC del trabajo, PC servidor oficina, y futuro VPS si aplica. |
| **Orquestación** | Coolify 4.x | Self-hosted Heroku alternative. Push GitHub → deploy automático con SSL. **Mata el deploy por USB.** |
| **Reverse proxy** | Caddy 2 (incluido en Coolify) | SSL automático con Let's Encrypt. |
| **Acceso público** | Cloudflare Tunnel (gratis) | Expone PC servidor de oficina al internet sin abrir puertos del router. Necesario para acceso desde fuera de la oficina (vendedores en ruta). |
| **Logs/observabilidad** | Sentry self-hosted (opcional) o `loguru` + archivos | Sentry self-hosted requiere recursos. Inicialmente usar `loguru` con rotación a archivo + página `/admin/logs` para Beto. |
| **Backups** | `pg_dump` + `rclone` → Backblaze B2 | $0.005/GB/mes. Off-site, versionado nocturno. |
| **Tests** | pytest 8 + pytest-django 4.9 + factory-boy 3 + Playwright (E2E) | NO NEGOCIABLE. Tests son lo que evita la regresión del CRM-ERP v4. |
| **Linting/format** | Ruff 0.6 + djLint 1.35 | Ruff sustituye flake8+isort+black. djLint para templates HTML. |
| **Gestor paquetes** | uv 0.4 | 10x más rápido que pip. Lockfile reproducible. |

## 4. Data Model

### Filosofía

- IDs son `BigAutoField` (no UUIDs) — más rápidos para joins, más legibles para debug. Para datos expuestos a clientes externos, agregar `external_id` UUID separado.
- Toda tabla hereda de `TimestampedModel` (`created_at`, `updated_at`) y la mayoría de `AuditedModel` (`created_by`, `updated_by`).
- Soft delete (`deleted_at`) en tablas con datos sensibles (clientes, ventas, facturas). Hard delete en tablas operativas (logs, sesiones de chat viejas).
- Multi-sucursal desde el día 1 vía FK `sucursal_id`. Las queries siempre filtran por sucursal del usuario salvo admin.

Semántica de los 5 niveles (validada contra SAP Retail, Oracle RMS, NetSuite, Dynamics 365, Odoo — 2026-04-11):

| # | Nivel | Ejemplo Cremería HM | Cardinalidad esperada |
|---|---|---|---|
| 1 | División | Perecederos / Abarrotes / No-alimentos | 3–5 |
| 2 | Departamento | Lácteos, Embutidos, Cárnicos, Secos, Limpieza | 10–20 |
| 3 | Categoría | Quesos, Cremas, Yogures, Jamones | 40–80 |
| 4 | Familia | Queso fresco, Queso madurado, Queso fundido | 100–200 |
| 5 | Subfamilia | Panela, Oaxaca, Adobera, Cotija | 300–600 |

El **SKU** (modelo `Producto`) es la hoja del árbol, NO un sexto nivel jerárquico.

**Regla clave**: `Producto.subfamilia` siempre apunta a `Categoria.nivel=5`. El árbol completo (División→Departamento→Categoría→Familia→Subfamilia) se obtiene navegando `parent` hacia arriba.

**Modelo de bodega en el catálogo** — El catálogo de productos es **global**. La disponibilidad por bodega se modela como atributo multi-valor (`Producto.bodega_disponible` ∈ {"CR", "AB", "CR,AB"}), no como duplicación de jerarquía. Esto sigue la best practice de SAP Retail, Oracle RMS, NetSuite, Microsoft Dynamics 365 y Wisys WMS: *una sola jerarquía maestra con asignación producto↔bodega, para preservar consolidación de reportes y evitar duplicación de master data*. Los reportes que requieran vista por bodega pivotan `Producto.bodega_disponible × Categoria.nivel_N` sin requerir duplicación del árbol.

## 5. Reporteador IA — Arquitectura completa (sección crítica extra)

Esta es la pieza diferenciadora. Tiene su propia sección porque la implementación es delicada — un error de seguridad aquí significa que un vendedor podría leer datos que no le tocan, o peor, modificar la BD.

### Pipeline completo

```
┌─────────────────────────────────────────────────────────┐
│ 1. INGRESO                                              │
│ Vendedor escribe en chat:                               │
│ "cuánta Salchicha San Antonio compró FDH en marzo?"     │
│ → POST /chat/<session_id>/message/ (HTMX)               │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│ 2. PERSISTENCIA INICIAL                                 │
│ - Guardar ChatMessage(role='user') en BD                │
│ - Calcular embedding (Voyage-3-lite, $0.02/M tokens)    │
│ - Guardar MessageEmbedding                              │
│ - HTMX swap: agregar burbuja del usuario al DOM         │
│ - HTMX swap: agregar "escribiendo..." del asistente     │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐

│ - Hash de (pregunta normalizada + user_id_o_rol)        │

│ - Ahorra ~30-40% del costo del API                      │
└────────────────────────┬────────────────────────────────┘
                         ▼ (si no hay cache)
┌─────────────────────────────────────────────────────────┐
│ 4. CLASIFICADOR (Haiku 4.5)                             │
│ Input: pregunta + esquema resumido (solo nombres tabla) │

│   {                                                     │

│ Reglas (todas obligatorias):                            │
│ a. Parser sqlparse extrae tipo de statement             │
│    → Solo SELECT permitido. UPDATE/DELETE/DROP/INSERT/  │
│      ALTER/CREATE/GRANT → REJECT inmediato              │

                         ▼
┌─────────────────────────────────────────────────────────┐
```

## 7. Frontend Architecture

### Filosofía

- **Server-rendered first.** Toda página entrega HTML completo en la primera request. HTMX solo intercambia fragmentos cuando el usuario interactúa.
- **Sin SPA.** No hay router cliente, no hay state global, no hay JSON. El estado vive en la BD y en el HTML.
- **Alpine.js solo para interacciones puramente locales:** toggles, dropdowns, modales sin red. Si requiere ir al server, usa HTMX.
- **ECharts para gráficas** se inicializa con `Alpine.data()` o con un script al final del partial HTMX.

### State Management

- **Server state**: Django models, queryset cache. Las vistas reciben request → query → render. No hay store cliente.
- **Form state**: HTMX maneja el formulario, valida server-side, devuelve errores como HTML parcial.
- **UI local state**: Alpine.js para cosas como "está abierto el dropdown del usuario", "está expandido el sidebar".
- **Chat state**: vive en `ChatSession` y `ChatMessage` en BD. Polling cada 3 segundos NO necesario porque HTMX hace el swap directo.
- **Real-time**: NO hay websockets. Si en el futuro necesitas notificaciones live, usa Server-Sent Events (SSE) vía `django-eventstream`.

### Reglas del modelo de sucursales

1. **Todo User tiene `sucursal_asignada` FK a Sucursal (nullable).**
   - NULL = admin de empresa → ve todo
   - NOT NULL = usuario de sucursal → ve solo esa sucursal (a menos que su rol sea de empresa como `cobranza` configurado así)

2. **Todo modelo transaccional tiene `sucursal_id` FK a Sucursal.**
   - Ventas, clientes, pedidos, facturas, inventario, gastos, comisiones, todos.
   - Este campo se asigna automáticamente en creación desde `request.user.sucursal_asignada` (si no es admin de empresa).

3. **Doble filtro en querysets:**
   - Primero filtra por `sucursal_asignada` del user (si tiene)
   - Luego filtra por rol (vendedor → sus clientes, supervisor → su equipo, etc.)
   - Admin de empresa = ambos filtros NO aplican

4. **Cambio de sucursal en corrida** (uso avanzado):
   - Un admin de empresa puede "ver como" una sucursal específica usando `?as_sucursal=CREM` en la URL. Útil para debugging o reportes enfocados.
   - Un usuario de sucursal NUNCA puede hacer esto.

### Implementación: SucursalFilterMixin + RoleFilteredQuerysetMixin

```python
# apps/core/mixins.py

class SucursalFilterMixin:
    """
    Filtra automáticamente el queryset por sucursal del usuario.

    - Si user.sucursal_asignada is None → admin_empresa → ve todo
    - Si user.sucursal_asignada is set → filtra por esa sucursal

    El campo que filtra por sucursal se controla con `sucursal_field`
    (default 'sucursal_id'). Si el modelo tiene un nombre diferente
    (ej: 'branch_id'), override en la vista.
    """
    sucursal_field = "sucursal_id"

    def get_queryset(self):
        qs = super().get_queryset()
        user = self.request.user
        if not user.is_authenticated:
            return qs.none()
        if user.is_superuser:
            return qs
        if user.sucursal_asignada is None:
            # Admin de empresa — ve todo
            # Permitir override vía ?as_sucursal=CREM para "ver como"
            as_sucursal = self.request.GET.get("as_sucursal")
            if as_sucursal:
                return qs.filter(**{self.sucursal_field: as_sucursal})
            return qs
        # Usuario de sucursal — solo su sucursal
        return qs.filter(**{self.sucursal_field: user.sucursal_asignada_id})


class RoleFilteredQuerysetMixin(SucursalFilterMixin):
    """
    Segundo filtro: por rol específico (vendedor → sus clientes, etc.).
    Hereda de SucursalFilterMixin para aplicar AMBOS filtros en cascada.
    """
    role_filters = {
        "vendedor": lambda qs, user: qs.filter(vendedor_asignado=user),
        "supervisor_ventas": lambda qs, user: qs.filter(
            vendedor_asignado__in=user.equipo.all()
        ),
        # admin_sucursal, cobranza, admin_empresa no tienen filtro adicional de rol
    }

    def get_queryset(self):
        # Primero aplica filtro de sucursal (del padre)
        qs = super().get_queryset()
        user = self.request.user
        # Luego aplica filtro de rol
        for group_name, filter_fn in self.role_filters.items():
            if user.groups.filter(name=group_name).exists():
                return filter_fn(qs, user)
        return qs
```

## 14. Testing Strategy

### Filosofía

> Los tests son la diferencia entre "cada cambio rompe algo" y "puedo refactorizar con confianza". Esto es **NO NEGOCIABLE.**

Cobertura mínima objetivo: **80%** en cada app, **100%** en `apps/chat_ia/pipeline/sql_validator.py`.

### Unit Tests (pytest + factory-boy)

- **Modelos**: validaciones, métodos custom, signals
- **Mixins**: `RoleFilteredQuerysetMixin` con cada rol
- **Services**: lógica de negocio (`ventas.services.crear_pedido`, etc.)
- **Pipeline IA**: cada componente aislado
- **Validador SQL**: TODOS los casos de seguridad de la Sección 5

```python
# Ejemplo: apps/chat_ia/tests/test_sql_validator.py
import pytest
from apps.chat_ia.pipeline.sql_validator import validate_sql, SQLValidationError

def test_rechaza_drop_table():
    with pytest.raises(SQLValidationError, match="Solo SELECT permitido"):
        validate_sql("DROP TABLE clientes;", user_context={'rol': 'admin'})

def test_vendedor_query_sin_filtro_es_rechazada():
    sql = "SELECT * FROM clientes LIMIT 10"
    user = {'rol': 'vendedor', 'id': 12}
    with pytest.raises(SQLValidationError, match="filtro de vendedor"):
        validate_sql(sql, user_context=user)

def test_vendedor_query_con_filtro_correcto_pasa():
    sql = "SELECT * FROM clientes WHERE vendedor_asignado_id = 12 LIMIT 10"
    user = {'rol': 'vendedor', 'id': 12}
    result = validate_sql(sql, user_context=user)
    assert result.is_valid
```

### Integration Tests (pytest-django)

- **Vistas HTMX**: client.get/post → assertions sobre HTML respuesta
- **API REST**: DRF test client
- **Auth flow**: login con cada rol → verificar accesos
- **ETL**: cargar fixture pequeño de CSV → verificar BD

### E2E Tests (Playwright)

Solo flujos críticos. NO hacer E2E de cosas que un unit/integration cubre.

- `test_login_flow.py`: usuario → login → ve dashboard

## 17. Reglas No Negociables (proyecto-nivel)

1. **El validador de SQL del chat IA es código de seguridad crítica.** Sus tests son blockers para deploy. Cualquier modificación requiere revisión obligatoria.

2. **Apps Django son módulos aislados.** Una app solo importa de `core` y de sí misma. Nunca cross-import. Hay un test automático que falla si se rompe.

3. **Los tests son no negociables.** Cobertura mínima 80%, 100% en `sql_validator.py`. Sin tests no hay merge.

4. **Comentarios en español, código en inglés.** Variables, funciones y clases en inglés (estándar Python). Comentarios y mensajes al usuario en español.

5. **Multi-sucursal desde el día 1.** Toda tabla con FK a `Sucursal`. Toda query filtra por sucursal del usuario salvo admin.

6. **Row-Level Security obligatorio.** Vendedor solo ve sus datos. Esto se verifica con tests E2E reales, no solo unit tests.

7. **Sin deploys manuales.** Todo deploy pasa por GitHub → Coolify. El deploy por USB del CRM-ERP v4 está prohibido y es la razón principal de existir de este proyecto.

8. **Presupuesto IA tope diario.** El sistema corta nuevas queries al chat IA si el gasto del día supera `CHAT_IA_DAILY_BUDGET_USD` (default $5/día). Beto recibe alerta.

9. **Backups verificados.** Cada lunes el sistema corre un test automático de restauración del último backup. Si falla, alerta.

10. **Tres golden paths siempre verdes (smoke tests pre-deploy)**:
    - Login como admin → ve dashboard con KPIs
    - Login como vendedor → solo ve sus clientes en `/clientes/`
    - Login como supervisor → /chat → pregunta "ventas de hoy" → recibe respuesta con SQL y datos correctos

11. **Auditoría inmutable.** El log de auditoría (`apps.auditoria.AuditLog`) NUNCA se borra ni modifica. Append-only. Es la única forma de reconstruir qué pasó cuando algo se rompe.

12. **Documentación viva en `docs/`.** Cada cambio arquitectónico actualiza `docs/arquitectura.md`. Cada cambio en el pipeline IA actualiza `docs/pipeline_chat_ia.md`. Cada cambio en ETL actualiza `docs/etl_punto_zero.md`.

## Apéndice A — Comparación con CRM-ERP v4 (qué arregla)

| Problema en CRM-ERP v4 | Solución en EspritOS |
|---|---|
| **Cada cambio rompe otra cosa** | Apps Django aisladas, una por dominio (pos, precios, cfdi, comisiones, etc.) + regla "no cross-import" con test automático + tests obligatorios por módulo |
| **Performance lento** | Django ORM con `select_related`/`prefetch_related` + índices diseñados desde el día 1 (ej: `Customer.vendedor_asignado` tiene índice explícito) + queries con `EXPLAIN ANALYZE` pre-merge. Para reportes pesados, queries SQL crudas en `apps.reportes` — sin ORM overhead. |
| **Deploy por USB** | Push GitHub → Coolify auto-deploy con SSL en < 5 min. Primero en PC del trabajo (WSL2), luego en PC servidor dedicada en oficina. |
| **Schema Prisma monolítico de 1543 líneas** | 72 modelos repartidos en 21 apps Django. Cada app tiene su `models.py` con 3-8 modelos relacionados. Claude no se pierde en archivos gigantes. |
| **Lógica de negocio en `src/lib/` mezclada** | Lógica en `apps/<app>/services/` con un archivo por dominio. Ej: `apps/cfdi/services/global_invoice.py` es la única fuente de verdad para facturas globales. |
| **Sin tests (0 archivos de test en CRM-ERP v4)** | Tests obligatorios por app, 80% cobertura mínima, 100% en `sql_validator.py` y servicios de POS (transacciones atómicas). CI bloquea merge si bajan. |
| **Sin observabilidad** | Loguru + dashboard `/admin/system/health/` con queries por minuto, costo IA acumulado, errores recientes. Alertas Telegram en warnings+. |

## Apéndice E — ETL desde Punto Zero EVO (estrategia completa)

> **Propósito:** Este apéndice es la **guía autoritativa** para el Paso 6 del Build Order. Si cualquier cosa del ETL no está aquí, consulta `context/revision-servidor/` que contiene el know-how probado (ya migraron exitosamente `datos9` Abarrotera al CRM-ERP v4).

### E.1 Contexto del servidor Punto Zero

- **Versión:** Punto Zero EVO
- **Motor BD:** MySQL (probablemente 5.x con tablas MyISAM) en un servidor Windows administrado por Beto + Bernardo
- **Bases de datos:** `datos1` (Cremería), `datos9` (Abarrotera — ya migrada al CRM-ERP v4 como referencia)
- **Encoding:** **latin1** (¡NO utf8!) — crítico para el transformer de encoding
- **Cliente instalado:** En la PC de Beto (la misma donde se construirá EspritOS durante desarrollo)
- **Usuario normal actual:** Beto exporta CSVs manualmente a fin de mes — vamos a reemplazar esto con el ETL automatizado

### E.2 Checklist del servidor (ejecutar ANTES del Paso 6)

Beto + Bernardo lo hacen juntos en ~15 min. Sin estos datos no se puede arrancar el ETL.

**1. Versión de MySQL**
```cmd
mysql --version
```
Ubicación típica: `C:\Program Files\MySQL\MySQL Server 5.x\bin\mysql.exe`

**2. ¿MySQL escucha en red o solo local?**
```cmd
netstat -an | findstr :3306
```
- `0.0.0.0:3306 LISTENING` → acepta conexiones remotas → **Plan C1 viable**
- `127.0.0.1:3306 LISTENING` → solo local → editar `my.ini` y cambiar `bind-address=0.0.0.0` (requiere reinicio del servicio) o usar Plan C2
- Nada → MySQL no expone TCP → Plan C2

**3. Firewall**
Agregar regla en Windows Firewall del servidor para permitir el puerto 3306 desde IPs de la LAN de oficina (NO de todo internet).

**4. Prueba de conexión desde la PC de Beto**
```powershell
Test-NetConnection <ip-servidor> -Port 3306
```
Si `TcpTestSucceeded: True`, el puerto está abierto y alcanzable.

**5. Usuarios actuales MySQL**
```sql
SELECT user, host FROM mysql.user;
```

**6. Crear usuario read-only para EspritOS** (si elegimos C1)
```sql
CREATE USER 'espritos_reader'@'192.168.%' IDENTIFIED BY '<password-segura>';
GRANT SELECT ON datos1.* TO 'espritos_reader'@'192.168.%';
GRANT SELECT ON datos9.* TO 'espritos_reader'@'192.168.%';
FLUSH PRIVILEGES;
```
⚠️ Usa `'192.168.%'` (o tu rango de LAN real), **NO `'%'`** — no queremos acceso desde internet.

**7. Tamaño estimado**
```sql
SELECT 
  table_schema AS db,
  ROUND(SUM(data_length + index_length) / 1024 / 1024, 2) AS mb,
  SUM(table_rows) AS rows_approx
FROM information_schema.tables
WHERE table_schema IN ('datos1', 'datos9')
GROUP BY table_schema;
```
Si <500MB y <5M filas, ETL inicial tarda <10 minutos.

**8. Horario seguro para ETL**
Confirmar con los usuarios de Punto Zero que las 2am-4am están libres (nadie factura, cierra caja ni corre respaldos).

### E.3 Decisión C1 vs C2

| Condición | Plan |
|---|---|
| Pasos 2, 4, 6 del checklist OK | **C1** — conexión directa |
| Puerto 3306 solo en localhost, no podemos cambiar `bind-address` | **C2** — dump nocturno + share |
| Firewall/políticas restringen LAN | **C2** |
| Servidor tiene poca RAM y queries pesadas lo tumban | **C2** (el dump es una operación controlada, el SELECT abierto puede ser impredecible) |

**Por defecto intentar C1 primero.** Es más simple y más fresco. C2 solo si C1 es imposible.

En `apps/etl/sources/punto_zero_mysql.py`:
```python
import pymysql
from django.conf import settings

class PuntoZeroMySQLSource:
    def __init__(self, db_name):
        self.db_name = db_name

    def connect(self):
        return pymysql.connect(
            host=settings.PUNTOZERO_HOST,
            port=settings.PUNTOZERO_PORT,
            user=settings.PUNTOZERO_USER,
            password=settings.PUNTOZERO_PASSWORD,
            database=self.db_name,
            charset=settings.PUNTOZERO_CHARSET,
            cursorclass=pymysql.cursors.DictCursor,
            connect_timeout=settings.PUNTOZERO_CONNECT_TIMEOUT,
            read_timeout=settings.PUNTOZERO_READ_TIMEOUT,
        )
```

### E.5 Configuración Plan C2 (dump nocturno)

**En el servidor** (tarea programada de Windows cada noche a las 1am):
```batch
@echo off
set DATESTAMP=%date:~6,4%%date:~3,2%%date:~0,2%
"C:\Program Files\MySQL\MySQL Server 5.x\bin\mysqldump.exe" ^
  -u root -p<password> ^
  --single-transaction --quick --skip-lock-tables ^
  datos1 > C:\dumps\datos1_%DATESTAMP%.sql

REM Copiar a share de red
copy C:\dumps\datos1_%DATESTAMP%.sql \\servidor\espritos-dumps\datos1_latest.sql
```

**En EspritOS** (`.env`):
```env
ETL_SOURCE=puntozero_mysql_dump
PUNTOZERO_DUMP_PATH=//servidor/espritos-dumps/datos1_latest.sql
# El ETL levanta un contenedor MySQL 5.7 local, importa el dump, lee de ahí
```

El contenedor MySQL local se define en `docker-compose.override.yml` (generado por el bootstrap cuando se elige C2).

### E.6 Mapeo de tablas Punto Zero → EspritOS

Referencia completa en `context/revision-servidor/output/schema/schema_resumen.md` (334 tablas de PZ, 80 con datos).

> **⚠️ Corrección post-verificación (2026-04-09):** Durante la prueba de `verify_pz_connection.py` contra el servidor real se descubrió que **varias tablas asumidas NO existen** en PZ EVO 5.1.48, y que **nombres de columna clave son diferentes** a los que usé en la primera versión del blueprint. Los nombres reales fueron verificados contra los scripts de RevisionServidor (`context/revision-servidor/scripts/05-08_*.py`) que ya migraron Abarrotera al CRM-ERP v4 exitosamente.
>
> **Tablas que NO existen en PZ (se quitaron del verify y preflight):**
> - ❌ `categorias` → la real es `lineas` (la columna en productos también es `Linea`, no `IdLinea`)
> - ❌ `cxc`, `cxp`, `gastos`, `cortes` → no existen con esos nombres. CxC real es `saldoscli`. CxP y gastos: verificar con `SHOW TABLES LIKE '%saldo%'`.
>
> **Correcciones clave de nombres de columna** (el campo real está en *itálicas*):
>
> **`productos`** — columnas reales: `Id, Clave, `*`Descrip`*` (NO Descripcion), Linea, SubLinea, Marca, Costo, CostoProm, Precio1-5 (5 listas embebidas), IVA, Existencia, UnidadMedida, ClaveSAT, Exento, ImpuestoAd, Comisionable, Proveedor1, FechaRegistro`. **NO tiene** `Activo`, `TasaIVA`, `TasaIEPS`, `EsExentoIVA`, `CostoRepo`, `DescripcionCorta`, `usesCategoryFormula`, `IdLinea`, `IdMarca`.

>
> **`proveedores`** — similar a clientes pero con `*`EMail`*` con **E mayúscula** (¡inconsistencia de PZ! Clientes usa `Email`, proveedores usa `EMail`).
>
> **`vendedores`** — solo 5 columnas: `Id, Clave, Nombre, Comision, ComisionPrecio1`. **NO tiene** email, teléfono, activo.
>
> **`tickets`** — `Id, `*`Venta`*` (no `Folio`), `*`Fecha`*`, `*`Hora`*` (campos **separados**, hay que combinar), Cliente (clave), Vendedor (clave), Total, IVA, Efectivo, TC, Descuento, Caja, Adicional`. **NO tiene** `Subtotal` (calcular), `MetodoPago` (inferir), `Cambio` (calcular), `Estatus`, `EsCredito`, `Notas`, `Serie`.

>
> **`facturas`** — `ID` con **mayúsculas** (¡diferente a `tickets.Id`!), `Factura` (folio), `Serie, Cliente, Fecha, Hora, Subtotal, IVA, ImpuestoAd, Descuento, Vendedor, MetodoDePago, FormaDePago`. **NO tiene** `Total` (calcular), `TotalImpuestos` (calcular), `UUID`, `xml_timbrado`, `RFCReceptor`, `NombreReceptor`. El UUID y XML viven en tabla `xmls` aparte.
>
> **`compras`** — `Id, `*`Compra`*` (folio, no `Folio`), `*`Proveedor`*` (clave, no `IdProveedor`), Fecha, Subtotal, IVA, ImpuestoAd`. **NO tiene** `Total`, `Estatus`, `TipoPago`, `FechaEsperada`, `Notas`.

> **`comprasdetalle`** — join al padre por `Compra` (el folio), **NO por `Id`**. `*`CostoBruto`*` (no `CostoUnitario`). `Desc1` (no `Descuento`).

### E.7 Transformaciones específicas (copiadas de RevisionServidor)

#### E.7.1 Encoding latin1 → utf8
```python
# apps/etl/transformers/encoding.py
def fix_latin1(text):
    """
    Punto Zero guarda texto en latin1. Si la conexión MySQL usa charset='latin1',
    los bytes llegan como latin1 pero pymysql los decodifica como utf8 si el cliente
    está en utf8 — causando 'mojibake' (Cremería → Cremerï¿½a).
    
    Solución: forzar re-encode manual.
    """
    if text is None:
        return None
    if isinstance(text, bytes):
        return text.decode('latin1', errors='replace')
    if isinstance(text, str):
        try:
            return text.encode('latin1').decode('utf-8', errors='replace')
        except (UnicodeDecodeError, UnicodeEncodeError):
            return text
    return str(text)
```

```python
# apps/etl/transformers/fechas.py
from datetime import date, datetime
from zoneinfo import ZoneInfo

TZ_MX = ZoneInfo("America/Mexico_City")

def clean_date(d):
    """Convierte fechas corruptas de PZ a None."""
    if d is None:
        return None
    s = str(d).strip()
    if s in ("0000-00-00", "0000-00-00 00:00:00", "", "NULL"):

        # Agregar timezone si no tiene
        if d.tzinfo is None:

        return d
```

#### E.7.3 RFC
```python
# apps/etl/transformers/rfc.py
import re

RFC_PATTERN = re.compile(r'^[A-ZÑ&]{3,4}[0-9]{6}[A-Z0-9]{3}$')

def normalize_rfc(rfc):
    """Normaliza RFC a formato SAT válido o None."""
    if not rfc:
        return None
    cleaned = rfc.strip().upper().replace(' ', '').replace('-', '')
    if cleaned in ('XAXX010101000', 'XEXX010101000'):  # genéricos SAT
        return cleaned
    if RFC_PATTERN.match(cleaned):
        return cleaned
    return None  # RFC inválido — loggeamos pero no bloqueamos la carga
```

**Estrategia de delta:**
1. Leer `ultima_fecha_procesada` de la tabla destino
2. Restarle **2 días** como buffer (por correcciones retroactivas en PZ)
3. Query MySQL: `SELECT * FROM tickets WHERE Fecha >= <buffer_date>`
4. UPSERT a Postgres con `ON CONFLICT (pz_clave) DO UPDATE SET ...`
5. Actualizar watermark al `max(Fecha)` de lo procesado

**Idempotencia:** Re-correr el mismo delta no debe duplicar. Esto lo garantiza el UPSERT por `pz_clave`.

### E.10 Plan de rollback

**Si el ETL corrompe datos en Postgres:**
1. `pg_dump` pre-ETL siempre (el Celery Beat task lo hace automáticamente)
2. Si algo sale mal: `docker compose exec db psql -U espritos -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"` (⚠️ destructivo)
3. Restaurar desde el último backup verificado
4. Resetear watermarks: `python manage.py etl_reset_watermark --all`
5. Re-correr el ETL inicial

**Si el ETL falla a mitad:**
- La transacción se hace por batch de 1000 registros con `ATOMIC_REQUESTS=True`
- Los batches exitosos quedan commiteados; el batch fallido se rollback
- El watermark NO se actualiza si el batch falla
- Siguiente run reprocesa desde donde falló

**Circuit breaker:**
Si 3 ejecuciones consecutivas fallan → alerta Telegram + pausar Celery Beat task hasta que Beto lo reactive manualmente con `python manage.py etl_resume`.

**Implicaciones técnicas:**

#### 1. Charset: latin1 obligatorio
MySQL 5.1 **NO soporta `utf8mb4`**. Solo `utf8` (3 bytes) y `latin1`. Como PZ guarda texto en `latin1` de forma nativa, usamos `latin1` en la conexión y aplicamos `fix_latin1()` (ver E.7.1) antes de escribir a Postgres.

```python
# CORRECTO
pymysql.connect(..., charset='latin1')
# Luego en el transformer:
nombre_utf8 = fix_latin1(row['Nombre'])

# INCORRECTO — causa mojibake
pymysql.connect(..., charset='utf8mb4')  # no existe en 5.1
pymysql.connect(..., charset='utf8')      # trunca emojis y lee latin1 mal
```

#### 2. MyISAM: sin transacciones, sin row-level lock
MyISAM bloquea **tabla entera** durante escrituras. Si el ETL lee una tabla grande con `SELECT * FROM historicoalmacen` mientras alguien está facturando, hay contención.

**Mitigaciones aplicadas en `punto_zero_mysql.py`:**
- Ventana de ejecución: **2:00-4:00 AM** (nadie está usando PZ) — confirmado con Bernardo
- `SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED` — permite leer sin esperar locks (dirty reads aceptables en ETL)
- `SSDictCursor` de pymysql — streaming server-side, no acumula filas en RAM
- Timeouts agresivos (10s connect, 180s read) para detectar problemas pronto

#### 3. Autenticación
MySQL 5.1.48 soporta dos tipos de hash de password:
- `mysql_native_password` (nuevo estilo, desde 4.1) — ✅ soportado por pymysql 1.1
- `mysql_old_password` (viejo estilo, pre-4.1) — ❌ no soportado por pymysql

**Cuando Bernardo cree el usuario `espritos_reader`, debe usar:**
```sql
CREATE USER 'espritos_reader'@'192.168.%' IDENTIFIED BY 'PASSWORD_AQUI';
-- NO usar: SET PASSWORD FOR ... = OLD_PASSWORD('...')
```

Si por alguna razón el usuario resulta con `mysql_old_password` (ej: por un setting global `old-passwords=1` en `my.ini`), hay dos fallbacks:

**A)** Corregir el hash:
```sql
SET old_passwords=0;
SET PASSWORD FOR 'espritos_reader'@'192.168.%' = PASSWORD('PASSWORD_AQUI');
```

**B)** Cambiar a `mysql-connector-python` (soporta auth antigua):
```bash
# pyproject.toml
"mysql-connector-python==8.4.*"  # tiene soporte para MySQL 4.1+ con auth vieja
```

Por defecto usamos **pymysql**, cambiamos si falla.

#### 4. Funcionalidades SQL NO disponibles
MySQL 5.1 carece de:
- **CTEs** (`WITH ... SELECT`) — no las usamos
- **Window functions** (`ROW_NUMBER() OVER`) — no las usamos
- **`JSON` type** — no aplica, PZ no guarda JSON
- **`GENERATED COLUMNS`** — no las usamos
- **`ONLY_FULL_GROUP_BY`** sql_mode — por eso desactivamos con `sql_mode='NO_ENGINE_SUBSTITUTION'`

Todas las queries del ETL son `SELECT ... WHERE ... ORDER BY ... LIMIT` básicos, compatibles con 5.1.

#### 5. Query optimizer antiguo
El optimizer de 5.1 es significativamente peor que 5.7/8. Consecuencias:
- **Usar índices explícitos siempre** — `WHERE Fecha >= ...` requiere índice en `Fecha`
- **Evitar subqueries correlacionadas** — se materializan muy lentamente
- **`EXPLAIN` de queries pesadas antes de usarlas en el ETL**
- Si una query tarda >60s, dividirla en batches con `LIMIT`+`OFFSET` o filtro por rangos de fecha

#### 6. SSL no disponible en LAN interna
MySQL 5.1.48 tiene soporte SSL limitado. Como la conexión es dentro de LAN de oficina aislada, **usamos conexión plain TCP sin cifrar**. Esto es aceptable porque:
- Tráfico NO sale de la LAN (la PC de EspritOS y el servidor están en la misma red)
- El servidor no acepta conexiones de fuera (firewall + bind-address a LAN)
- Las credenciales viajan cifradas via `mysql_native_password` hashing

**Si en el futuro el tráfico debe salir de la LAN** (ej: acceso remoto con Cloudflare Tunnel al puerto 3306), habría que actualizar MySQL a 5.7+ o usar un proxy con SSL termination. No es prioridad ahora.

- **20:30 (8:30pm)** — Backup previo de Postgres EspritOS a Backblaze B2 (30 min antes del ETL por si algo sale mal)
- **23:00 (11pm)** — Si `datos9` está en modo `live` (ver E.15), segundo ETL one-shot o incremental de Abarrotera

El horario 21:00 es mejor que el original 2am porque:
1. **Más temprano** — Beto todavía está en su PC si algo falla
2. **Logs inmediatos** — Beto puede ver el resultado antes de dormir
3. **Retries más tempranos** — 5min/15min/45min caen dentro de la ventana libre
4. **Cero fricción con usuarios** — nadie en oficina hasta 7am, dando 10h de margen

**Recomendación para Bernardo:** agregar un respaldo diario de `datos1` con `mysqldump` a las 20:00 (8pm, una hora antes del ETL):
```batch
REM C:\Tasks\backup_datos1.bat — corre 20:00 (8pm) diario
@echo off
set DATESTAMP=%date:~6,4%%date:~3,2%%date:~0,2%
"C:\Program Files (x86)\MySQL\MySQL Server 5.1\bin\mysqldump.exe" ^
  -u root -pPASSWORD ^
  --skip-lock-tables ^
  datos1 > C:\backups\datos1_%DATESTAMP%.sql

REM Rotar: mantener solo últimos 14 días
forfiles /p C:\backups /m datos1_*.sql /d -14 /c "cmd /c del @path"
```

⚠️ `--skip-lock-tables` es obligatorio porque MyISAM: `--single-transaction` NO funciona sin InnoDB.

Este respaldo de Bernardo es independiente del ETL de EspritOS — es para seguridad del servidor en sí. Si algo pasa con `datos1` (corrupción, ataque, error humano), hay backup del día anterior.

### E.15 Arquitectura multi-sucursal + multi-source

> **Problema de diseño histórico que EspritOS resuelve:** Punto Zero EVO almacena Cremería HM (`datos1`) y Abarrotera HM (`datos9`) como **empresas separadas** porque así se diseñó PZ hace años — una limitación del software, no una realidad del negocio. En la realidad son **dos sucursales de la misma empresa madre** propiedad de Beto y su familia. EspritOS consolida ambas en la empresa real con `sucursal_id`, y los permisos (ver Sección 9) distinguen entre admins de empresa (ven todo) y admins de sucursal (solo la suya).

#### Mapeo de bases a sucursales (realidad vs PZ)

| Base PZ (así lo ve PZ) | Empresa real | `sucursal_id` EspritOS | `code` | Estado | Horario |
|---|---|---|---|---|---|
| `datos1` | Cremería HM | `1` | `CREM` | Activa | 7am-4pm |
| `datos9` | Abarrotera HM | `2` | `ABAR` | Activa | 7am-4pm |

**Ambas son sucursales de una sola empresa madre.** EspritOS es el primer sistema que las trata así correctamente.

#### Cómo las lee el ETL

Ambas bases viven en el **mismo servidor MySQL** (`192.168.0.200:3306`) — solo son databases distintas dentro del mismo servicio MySQLPZ. El usuario `espritos_reader` necesita permisos en ambas:

```sql
GRANT SELECT ON datos1.* TO 'espritos_reader'@'192.168.%';
GRANT SELECT ON datos9.* TO 'espritos_reader'@'192.168.%';
```

El ETL incremental nocturno corre **dos veces** cada noche (una por cada base), ambas dentro de la ventana 9pm-7am:

```
20:30 — Backup Postgres EspritOS → B2 (una sola vez)
21:00 — ETL incremental datos1 → Postgres EspritOS (sucursal_id=1)
22:00 — ETL incremental datos9 → Postgres EspritOS (sucursal_id=2)
23:00 — Stats log + alerta si hubo errores
```

Usa la misma conexión LAN C1 para ambas — solo cambia el `USE datos1` / `USE datos9` en la sesión MySQL.

#### Asignación de `sucursal_id` en los extractors

El mapeo es estático en `apps/etl/sucursales.py`:

```python
SUCURSAL_MAP = {
    "datos1": {"id": 1, "code": "CREM", "nombre": "Cremería HM"},
    "datos9": {"id": 2, "code": "ABAR", "nombre": "Abarrotera HM"},
}

def get_sucursal_id(source_db: str) -> int:
    return SUCURSAL_MAP[source_db]["id"]
```

Cada extractor recibe `source_db` como parámetro y automáticamente asigna `sucursal_id` al transformar la fila:

```python
# En BaseExtractor.run()
sucursal_id = get_sucursal_id(self.source_db)

# En transform(row)
return {
    "pz_clave": f"{source_db}:{row['Clave']}",  # prefijo para evitar colisiones
    "sucursal_id": sucursal_id,
    # ... resto de campos
}
```

#### Prefijo en `pz_clave` para evitar colisiones

PZ usa claves de negocio (ej: `CLI-001`, `VTA-000042`). Las mismas claves pueden existir en ambas bases pero ser entidades distintas. Para evitar colisiones en el UPSERT `ON CONFLICT (pz_clave)`, prefijamos con el nombre de la base:

```
PZ: datos1.clientes.Clave = "CLI-001"  → EspritOS.Cliente.pz_clave = "datos1:CLI-001"
PZ: datos9.clientes.Clave = "CLI-001"  → EspritOS.Cliente.pz_clave = "datos9:CLI-001"
```

Las dos filas coexisten con diferente `sucursal_id` y el reporteador IA las distingue al vuelo.

#### Watermarks por tabla × sucursal

Cada watermark es la combinación (tabla, source_db). Dos watermarks simultáneos:

```
tabla=tickets, source_db=datos1, last=2026-04-08 23:59:59  → se actualiza diario
tabla=tickets, source_db=datos9, last=2025-02-24 18:00:00  → nunca se actualiza (baja)
```

Esto permite al ETL correr datos1 cada noche (incremental) y datos9 una sola vez (one-shot), sin confundirse.

#### Orden del ETL incremental nocturno

```
21:00 — Backup Postgres EspritOS → B2 (Celery task backup_postgres_to_b2)
21:05 — ETL incremental datos1 → Postgres (Celery task etl_incremental_datos1)
21:30 — Si modo live y primera vez: ETL one-shot datos9 → Postgres
        (después de la primera noche, datos9 se salta automáticamente)
22:00 — Stats log + alerta si hubo errores
```

#### Grant MySQL para cubrir ambas bases (si modo `live`)

```sql
CREATE USER 'espritos_reader'@'192.168.%' IDENTIFIED BY 'PASSWORD_SEGURA';
GRANT SELECT ON datos1.* TO 'espritos_reader'@'192.168.%';
GRANT SELECT ON datos9.* TO 'espritos_reader'@'192.168.%';  -- solo si datos9 existe
FLUSH PRIVILEGES;
```

Si modo es `backup` (datos9 solo en respaldo), el grant solo incluye `datos1`. Para datos9 se levanta contenedor local sin autenticación LAN.

#### Reportes consolidados vs por sucursal

El reporteador IA respeta el alcance de forma transparente:

| Pregunta del supervisor | Query SQL generada |
|---|---|
| *"ventas totales de marzo"* | `WHERE fecha >= '2026-03-01'` (consolidado, ambas sucursales) |
| *"ventas de Cremería en marzo"* | `WHERE fecha >= '2026-03-01' AND sucursal_id = 1` |
| *"comparar Cremería vs Abarrotera en 2024"* | `GROUP BY sucursal_id` |

El SQL generator de Sonnet tiene en su contexto el mapa de sucursales, así que sabe que:
- "Cremería" / "principal" / "matriz" → `sucursal_id = 1`
- "Abarrotera" / "Abar" → `sucursal_id = 2`
- Sin mención explícita → consolidado (ambas)
